# Обслуживание

Системные операции для поддержания производительности фильтров. Большинство задач выполняется автоматически — здесь они для ручного запуска и диагностики.

## Индекс фасетов

Главный блок вкладки. Денормализованный индекс значений фильтров (color, size, price, weight и т.п.) — заменяет JOIN'ы по таблицам товаров и опций при каждой фильтрации. Фильтры начинают работать в 5–10 раз быстрее на каталогах от 10 000 товаров.

### Когда индекс обновляется автоматически

- При **сохранении набора фильтров** — пересобираются только изменённые ключи
- При **сохранении или удалении товара** через админку MODX — точечно для этого товара (плагин на `OnDocFormSave` / `OnResourceDelete`)
- После **CSV-импорта MS3** (`msOnAfterImport`) — полная пересборка
- Каждые **5 минут** через Scheduler-задачу `mfl_sync_facet_index` — догоняет правки через API и SQL-импорты, если у них обновлён `editedon`
- При **upgrade пакета** — задача `mfl_rebuild_facet_index` ставится в очередь Scheduler
- При нажатии кнопки **«Переиндексация»** в шапке админки

### Когда нужна ручная пересборка

- После **прямого SQL** без обновления `editedon` (sync-задача такие правки не видит)
- После **DELETE FROM** в базу напрямую (нет триггера, sync не справится)
- При обнаружении расхождений между фильтрами и реальными товарами
- Для подстраховки после крупных импортов — на всякий случай

Подробнее: [Cookbook: Синхронизация индекса фасетов](/components/mfilter/cookbook/facet-index-sync).

### Кнопки

| Кнопка | Когда использовать |
|--------|--------------------|
| **Пересобрать сейчас** | Маленький каталог (до 30k товаров) — займёт секунды |
| **Через Scheduler** | Большой каталог (50k+) или нет уверенности во времени выполнения. Появляется только если установлен Scheduler |

При выборе «Через Scheduler» сборка запускается на ближайшем тике cron — обычно в течение минуты. Параллельно сайт работает на fallback'е, простоев нет.

### Две пересборки одновременно не идут

Пересборка начинается с очистки обеих таблиц индекса и наполняет их заново — на крупном каталоге это минуты. Вторая пересборка выбросила бы всё, что успела записать первая, и окно, когда фильтры показывают неполный набор значений, растянулось бы на обе. Поэтому вторая не запускается.

Содержимое индекса от такого столкновения не терялось: после окончания обеих пересборок он полный. Дорого другое — каталог читается дважды, окно неполных значений вдвое длиннее, а кэш, набравшийся за это время, держит их ещё до часа (`mfilter.cache_lifetime`).

Что происходит вместо этого:

| Кто просит пересборку | Что будет |
|---|---|
| Задача планировщика | Встанет в очередь на две минуты позже и дождётся своей очереди |
| Кнопка в админке | Покажет предупреждение «Уже выполняется» и ничего не запустит |
| Синхронизация каждые 5 минут | Пропустит такт и вернётся в следующий, ничего не потеряв |
| Импорт MS3 без планировщика | Пересборка будет пропущена, в логе — предупреждение |

Ожидающий запуск не отменяет работу, ради которой его поставили: он выполнится после того, как освободится индекс, и прочитает каталог заново.

Так же защищены индексация значений TV и генерация алиасов. У алиасов последствия столкновения были хуже всего: обход проверяет, есть ли алиас, и только потом вставляет его, а уникальный ключ здесь не спасает — в него входит `culture_key`, и на сайте без культур он пустой. Два параллельных обхода записывали одному значению два алиаса.

### Статусы

| Статус | Что означает |
|--------|--------------|
| **Активен** (зелёный) | Индекс построен и используется |
| **В очереди Scheduler** (синий) | Сборка запланирована, выполнится на ближайшем тике |
| **Не построен** (жёлтый) | Индекс пустой. Нажмите «Построить сейчас» — без него фильтры работают по старому медленному пути |

### Метрики

| Метрика | Описание |
|---------|----------|
| **Текстовых записей** | Кол-во строк в `mfl_facet_index_text` (бренды, цвета, размеры) |
| **Числовых записей** | Кол-во строк в `mfl_facet_index_num` (price, weight) |
| **Последняя пересборка** | Дата и время последнего полного rebuild |

## Кэш данных фильтров

Промежуточные результаты вычислений — suggestions, фильтрованные ID. Очищается автоматически при сохранении товара или конфигурации фильтров.

**Очищать вручную нужно только при отладке расхождений данных.** В нормальной работе кэш не трогают.

## Прогрев baseIds (Legacy)

Старая система прогрева — заранее вычисляет набор ID товаров для страниц.

После стабилизации индекса фасетов будет упрощена или удалена. Сейчас ещё используется для AJAX-режима получения baseIds. **Не отключайте, если не уверены.**

Подробнее: [Прогрев кэша](warmup).

## Кнопка «Переиндексация» в шапке

Единая кнопка в правом верхнем углу админки запускает две независимые работы:

- **индекс TV, алиасы значений фильтров и очистка кэша** — строго в этом порядке: алиас строится из подписи, которую держит индекс TV, а кэш очищается последним, иначе за время пересборки он наполнится наполовину обновлёнными данными;
- **сборка индекса фасетов**.

Порядок между этими двумя работами не задан: с планировщиком обе уходят в очередь и выполняются в том порядке, в каком он до них доберётся.

Алиасы строятся по наборам фильтров — так же, как кнопкой «Сгенерировать» на вкладке «Алиасы». Обе кнопки и задача планировщика дают один результат.

Кэш подсказок после сборки индекса фасетов не сбрасывается: если сборка шла долго, часть подсказок какое-то время останется со старыми числами. Чтобы не ждать, нажмите «Очистить кэш» на этой же вкладке.

Полезна после массовых изменений в каталоге.

**Подсветка:**

- Серая — индекс актуален, при необходимости можно перезапустить
- Жёлтая — индекс ещё не построен, нажмите для первой сборки

Если установлен Scheduler — в фон уходят оба шага: индекс TV с алиасами и сборка индекса фасетов. Кнопка отвечает сразу, работа выполняется на ближайшем тике cron.

Без Scheduler всё выполняется синхронно, и страницу нужно дождаться. На крупных каталогах обход наборов занимает минуты и может упереться в таймаут веб-сервера. Тогда в сообщении будет сказано, ответа какого шага не дождались: сама работа при этом обычно продолжается на сервере, поэтому нажимать второй раз сразу не стоит — пойдёт ещё один такой же обход.

::: warning Проверьте, что cron планировщика работает
Если Scheduler установлен, но его cron не настроен, задача встанет в очередь и не выполнится: кнопка отчитается, что работа запущена, а данные останутся прежними. Очередь видна в разделе Scheduler — у выполненной задачи заполнено время запуска.
:::

## Диагностика

### Индекс пустой / suggestion'ы возвращают 0

1. Проверить статус индекса на вкладке Обслуживание
2. Если «Не построен» — нажать «Построить сейчас»
3. После сборки проверить количество записей — должно быть > 0

### После импорта товары не появляются в фильтрах

Индекс не обновляется автоматически при прямых SQL-вставках. Нужна ручная пересборка через **«Пересобрать сейчас»**.

### Долгая сборка зависает

Если кнопка «Пересобрать сейчас» не возвращается на каталогах 100k+:

1. Установите [Scheduler](https://github.com/modxcms/scheduler)
2. Используйте кнопку «Через Scheduler» — сборка уйдёт в фон без HTTP-таймаута

### Логи

Сборка пишет в лог MODX:

```
[mFilter] Facet index rebuild started
[mFilter] Facet index: indexed 145320 rows for 'color'
[mFilter] Facet index: indexed 87234 rows for 'size'
[mFilter] Facet index rebuild done: 8 filters, 450320 text rows, 12845 num rows, 8432ms
```
